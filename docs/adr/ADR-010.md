# ADR-010: Phased Customer Job Execution Model

**Status:** Accepted  
**Decision date:** 2026-11-13

## Context

PulseFlow needs a reliable job execution model that supports an initial production-ready MVP while allowing future expansion into customer-controlled execution environments.

Three execution approaches were evaluated:

1. Platform-managed handlers.
2. Customer-hosted workers.
3. Controlled HTTP execution.

Implementing customer-hosted workers immediately would increase MVP complexity through worker registration, authentication, heartbeats, leases, SDK development, and additional security boundaries.

## Decision

Adopt a phased execution strategy.

### Phase 1: MVP

Use platform-managed job handlers running on PulseFlow's own worker infrastructure.

The API accepts job requests, persists job records, and publishes execution events through the transactional outbox. The worker consumes eligible jobs and executes registered handlers.

MVP requirements:

- Platform-managed handlers.
- Queue-based asynchronous execution.
- Job retries and failure handling.
- Configurable execution timeouts.
- Job attempt tracking.
- Idempotent execution.
- Job status and execution history.
- Structured execution logging.

### Phase 2: Future expansion

Introduce customer-hosted workers.

Customers will be able to operate workers in their own infrastructure and connect them to PulseFlow through a secure worker protocol.

Future capabilities may include:

- Worker registration and authentication.
- Worker heartbeats and health monitoring.
- Worker leases and execution ownership.
- Worker SDKs.
- Customer-controlled execution environments.
- Worker capability and queue assignment.

These features are explicitly excluded from MVP scope.

## Architectural constraints

1. Keep job submission independent of the underlying execution location.
2. Define stable job and execution contracts.
3. Keep execution infrastructure behind clear application boundaries.
4. Do not introduce customer-hosted worker infrastructure during MVP development.
5. Preserve compatibility with future worker-based execution.
6. Maintain at-least-once delivery and idempotency guarantees.

## Database implications

The current database design remains valid for the MVP.

The worker registry decision, DB-015, remains deferred until Phase 2.

Do not create worker registration tables or worker lifecycle infrastructure as part of MVP implementation unless a separately approved decision requires them.

## Consequences

**Positive**

- Lower MVP implementation complexity.
- Faster path to a functional platform.
- Clear separation between job submission and execution.
- Future support for customer-controlled execution.

**Trade-offs**

- Initial execution is controlled by PulseFlow.
- Customers cannot run their own workers in the MVP.
- Phase 2 will require additional infrastructure and security design.

## Review conditions

Revisit this decision before starting Phase 2.

Any change to the MVP execution model requires a new ADR or an explicit superseding decision.
